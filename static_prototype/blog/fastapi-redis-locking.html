Preventing Race Conditions with FastAPI & Redis Distributed Locks

Building atomic seat reservations and high-concurrency ticket release engines with Redis TTL keys and Python Asyncio.

S
Soyal Senior Backend Developer • Kathmandu, Nepal

1. The High Concurrency Challenge

When launching high-demand ticket releases or flash sales, thousands of incoming HTTP requests attempt to reserve the exact same seat resource simultaneously. Standard SQL UPDATE queries result in lock wait timeouts or double-booking race conditions.

2. Implementing Redis Key Lock (SET NX EX)

Using Redis' atomic SET key value NX EX seconds command, only the first request acquires the lock key. Subsequent requests within the TTL window receive an immediate lock failure response without stressing the SQL database.

# Async Redis Lock Acquisition in FastAPI
@router.post("/reserve-seat")
async def reserve_seat(seat_id: str, user_id: int):
  lock_key = f"lock:seat:{seat_id}"
  acquired = await redis.set(lock_key, user_id, nx=True, ex=600)
  if not acquired:
    raise HTTPException(status_code=409, detail="Seat is currently held by another user")
  return {"status": "reserved", "expires_in_seconds": 600}

3. Summary

Shifting short-lived locks into in-memory Redis drastically improves backend throughput and eliminates database contention during surge traffic events.
