Case Study FastAPI • Redis • PostgreSQL

Cinema Ticket Reservation Engine

Designing a high-concurrency seat reservation API using FastAPI async workers, temporary Redis locks, and idempotent payment webhooks.

My Role Backend Architect
Tech Stack FastAPI, Redis, Postgres
Primary Problem Race Condition Locking
Lock Duration 10 Minutes (TTL)

1. Problem Statement

During blockbuster movie ticket releases, thousands of users hit the seat selection screen simultaneously. Standard SQL row updates cause database lock contention or double bookings when two customers select Seat E-12 at the exact same millisecond.

2. Redis Distributed Lock Strategy

We implemented a 10-minute temporary seat reservation mechanism in Redis before committing the ticket record to PostgreSQL.

# FastAPI Seat Lock Endpoint
@router.post("/showtimes/{id}/reserve")
async def reserve_seats(showtime_id: int, seats: List[str], user_id: int):
  lock_key = f"lock:showtime:{showtime_id}:seat:{seat}"
  # Acquire Redis Key with 600 second expiration
  acquired = await redis.set(lock_key, user_id, nx=True, ex=600)
  if not acquired:
    raise HTTPException(status_code=409, detail="Seat temporarily held by another user")
  return {"status": "reserved", "ttl": 600}

3. Outcomes

  • Zero double bookings registered across 50,000+ test ticket transactions.
  • PostgreSQL CPU utilization dropped by 65% because unconfirmed hold attempts stayed entirely inside in-memory Redis.
